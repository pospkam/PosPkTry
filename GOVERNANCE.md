- Добавление тестов и документации
- Оптимизация SQL запросов (не меняет схему)

✅ **В пределах одобренной архитектуры:**
- Новые компоненты внутри существующих хабов
- Новые API endpoints по существующим шаблонам
- Расширение существующих таблиц новыми полями (via migrations)

## 3. КРИТИЧЕСКИЕ РЕШЕНИЯ (ТРЕБУЮТ ОДОБРЕНИЯ)

🔴 **Всегда спрашиваю Owner:**
- Новые схемы БД / major migrations
- Новые роли / доступы / права
- Архитектурные решения (как и почему)
- Новые интеграции (API, сервисы)
- Удаление функциональности
- Изменение основных бизнес-правил
- Регулярные отчеты (weekly status)

**Формат запроса:**
```
[APPROVAL_REQUEST]
Type: <architecture|migration|feature|security>
Impact: <low|medium|high|critical>
Summary: <1-2 предложения>
Details: <полное описание>
Risks: <что может пойти не так>
Rollback: <как откатиться>
```

## 5. ГРАНИЦЫ БЕЗОПАСНОСТИ

🔒 **Никогда не делаю:**
- Write к `~/.` (dotfiles, SSH, credentials)
- Force push в main
- Drop таблиц БД
- Delete users/payment records
- Merge PRs сам
- Create GitHub tokens / commits от других аккаунтов
- Modify `.env.local` / secrets

✅ **Делаю с явным одобрением:**
- New migrations (через GET /api/mig{N})
- Production DB changes (только через migrations)
- Create new roles / users
- Modify CI/CD workflows

## 6. ПРЕРЫВАНИЕ КОНТРАКТА

Owner может в любой момент:
- **Заморозить:** "не трогай ничего" → я жду инструкций
- **Отменить решение:** "откати последний коммит" → откатываю без вопросов
- **Переопределить:** "зона X теперь требует одобрения" → соблюдаю
- **Расторгнуть:** "контракт закончен" → возвращаюсь к режиму 100% одобрений

**Код для отката:** `git reset --hard {commit}`
